# CLAUDE.md - "Who am I?" Game

## Project Overview
Web application to play the "Who am I?" guessing game remotely with friends and family. Players join a room by a 6-character code, assign secret characters to each other, then guess who they are. Adaptive UI works on desktop and mobile browsers; installable as a PWA.

- **Production:** https://whoami.escapist.club/ (Cloudflare Workers, free plan)
- **Repository:** https://github.com/mikhail-e/whoami-game — public, a showcase (see Decisions)
- **Stack:** Cloudflare Workers + Durable Objects backend (one Durable Object per room, `wrangler`); vanilla JavaScript (ES6+) + Bootstrap 5 frontend (a local copy); Jest and Playwright for tests. No build step, no frontend framework.

## Commands
```bash
npm install                        # Install dependencies (Node.js 22+: wrangler needs it)
npm start                          # wrangler dev: the Worker, its rooms and the files on http://localhost:8787
npm test                           # All checks: ESLint, Jest, then Playwright — run before every merge
npm run lint                       # ESLint only (any warning fails); npm run lint:fix fixes what it can
npx jest tests/game-logic.test.js  # Run a single Jest file
npm run test:e2e                   # Browser tests only (Playwright); :headed and :ui variants
npm run test:e2e:prod              # Browser tests against production (after a release)
npx playwright install chromium    # Once per machine: the browser for the tests
npx wrangler login                 # Once per machine: the owner's Cloudflare account, for the live log
npx wrangler tail whoami-game      # The live log of production; production is deployed by Workers Builds from master, never by hand
```

### How it works
- **Rooms are Durable Objects:** one per 6-character room code (e.g. `ABC123`), found by the code (`env.ROOMS.getByName(code)`); a room keeps its one game in its storage. The static files of `public/` are served without the Worker (they cost nothing of the day's request limit); `run_worker_first` in wrangler.jsonc sends `/api/*`, `/game/*` and `/ws/*` to `worker/index.js`, and `/game`, `/index`, `/404` too: the static files would answer those with a page, the game answers its 404 page
- **HTTP API:** `POST /api/create-game` (the Worker picks a code, the room takes the game only when it has none; a taken code is tried again), `POST /api/join-game` (a body over 64 KB is refused with 413 — the largest join carries one photo avatar; the room gets the join's fields only, each a text or nothing, so nothing nested reaches it); `GET /api/version` (the version from package.json, shown in the footer of both pages by `showAppVersion()` in utils.js); `GET /game/:roomCode` checks the code format first (a code that is no room code never reaches a room: random addresses would create rooms), then serves game.html when the room has a game or redirects to `/?error=room-not-found`. A room asked about but without a game writes nothing. HEAD gets what GET would, without the body. Should anything fail, the Worker answers `{ success: false }` with status 500 and the security headers, never Cloudflare's error page. Any address nothing else answers gets `public/404.html` with status 404
- **Security headers:** the Content Security Policy, Referrer-Policy, Permissions-Policy, nosniff — the list of the owner's Flying Solo — on every answer: `public/_headers` puts them on the static files (pages, files, the 404 page, their redirects), and the Worker on its own answers (API, room pages, its redirects) from `worker/security-headers.json`. The two are deliberate copies (`tests/security-headers.test.js` keeps them equal); the reasons are written in `_headers`, as JSON holds no comments. An accepted socket's answer goes back without them
- **Socket events:** the room page's socket is a `RoomSocket` (room-socket.js) on `/ws/CODE`; messages are JSON `{ event, data }`. Events: `join-room`, `assign-character`, `start-game`, `reveal-character`, `restart-game`, `leave-game`; for joining a started game `ask-to-join`, `admit-player`, `decline-player` (below). The room's broadcasts reach every player socket, the sender's included — intentional, keep it so. A message that is not JSON `{ event: string }` gets no answer, an unknown event neither, and a handler that fails answers "Something went wrong, please try again": nothing a page sends can break the room (room-base.js, `webSocketMessage`). **Who acts is the player the socket is registered for** (`join-room`, after checking the secret: the socket's role in its attachment), never an ID from the message — the events carry only what the move needs (`assign-character`: the target `playerId` and the `character`). A socket that is not registered gets "You are not in this game" and hears nothing of the room; a leaver's tabs all leave it. So the page sends its moves through `sendMove()` (game-room.js), which holds them while the socket is (re)joining or not connected — after a reconnect the new socket joins only once the HTTP join is back
- **Leaving:** a player leaves only themselves (`leave-game` acts for the socket's player, no kicking others); leaving in one tab takes the player out in all of them. A page whose socket asks into the room (`join-room`) only after its player has left — in another tab, at that very moment — or after the room is gone is answered with `player-left` for itself and goes home too: it drew the room from its HTTP join, and without the answer it would stay in a room it never hears. `removePlayerFromGame` drops the player, their character and reveal status; the last player leaving deletes the game and the room's storage (the old link leads home). The `player-left` broadcast carries the full state; the leaver redirects to `/?join=CODE` (prefilled rejoin) and the landing page remembers the last used name and avatar (`whoami-player-name` / `whoami-player-avatar` in localStorage, saved on create/join; the saved avatar is placed first in the grid so it gets auto-selected, and is ignored if it's neither in `avatarPool` nor a valid custom data URL)
- **Returning to a started game:** leaving a started round snapshots the player into `game.recentlyLeft` (character, reveal status, sticker color, join time). Joining with the same `playerId` restores everything and consumes the snapshot, without asking anybody; a stranger has to ask (below). Restart clears the snapshots. The `player-joined`/`player-reconnected` broadcasts carry `characters`/`revealedPlayers` so other clients see the restored character reappear
- **Joining a started game:** a newcomer (a valid ID that is neither in the list nor in `recentlyLeft`) gets `{ success: false, waitingForApproval: true }` from `/api/join-game` (status 200, not an error); the landing page opens the room page as on a join, and the room page shows `#waitingSheet` (the wax seal with an arc running round it; `body.waiting-for-admission` hides the room) and sends `ask-to-join` over its socket. Only then does the server record the request (`game.joinRequests`, `requestToJoin` in game-logic.js) and send the players `join-requested`; the waiting socket's role is `waiting`, never `player`, so it never acts for a player and the newcomer hears nothing of the room. Any player answers in `#joinRequestModal` (`admit-player` / `decline-player`); the first answer decides, a later one gets "This request has already been answered", which the page drops silently. Every end of a request reaches the players as `join-request-closed` and the newcomer as `join-request-ended`: `declined` sends them home (`/?join=CODE&error=join-declined`, they may ask again), `retry` makes the page join again and follow the answer - let in (`admitPlayer`: last in the list, the secret recorded), the lobby after a restart, or a room that is gone. A request lives as long as the newcomer's waiting pages: the last one's disconnect withdraws it (`withdrawJoinRequest`), a reconnect asks again. Requests are kept in the room's storage, so they outlive the room's sleep; a room that went down with its sockets withdraws, as it loads, every request without a waiting page. A newcomer may ask while players and waiting newcomers together are under 12, and is let in only while there is a seat (a leaver returning to the round may take it first: `admitPlayer` answers "Game is full" and the request stays). The waiting screen keeps the phone awake (`keepScreenAwake`): a sleeping phone loses its socket, and with it the request. The window has a static backdrop and no ×: only its buttons close it (otherwise a player could lose the request with no way back); requests queue, wait for another open window to close (`hidden.bs.modal`), and a page that opens gets the ones still waiting with `game-state` (`joinRequests`). The let-in newcomer has no character: their own card shows `.character-sticker.mystery.open-envelope` ("empty for now", nothing to press), the others get "+ Assign character" on it. So the room keeps inviting during a round: the room code ticket stays in the header, and the lobby's invitation (`#shareCard`, with the link field, at the top) gives way to a shorter one below the game controls (`#gameInviteCard`: a line saying a newcomer will ask, Copy Link and Share) — the round's screen starts with the players
- **Player list order:** `game.players` is kept in first-join order (`sortPlayersByJoinTime` sorts by `joinedAt` after every add), identical on every client — no client-side sorting. A player returning to a started round gets their old position back (the snapshot carries `joinedAt`); lobby rejoins go to the end
- **Persistence:** the room saves its game after every change (`gameToStorage` / `gameFromStorage` in game-logic.js: everything as it is — the clocks, `recentlyLeft`, the hashes of the secrets, the join requests) and loads it when it wakes: Cloudflare puts a room to sleep between messages and may take it out of memory at any moment, so nothing lives only in memory. A room no page of a player has open is deleted 2 hours after the last one closed (`ROOM_EMPTY_MS`, the owner's decision: a group that took a long break comes back to its room; a room nobody ever opened goes the same way); the last player leaving deletes it at once. The room's timer (alarm) does it, and the times are in `roomAlarmTime()` (game-logic.js)
- **Player identity:** one UUID per browser stored in `localStorage.playerId` (created in utils.js as `PLAYER_ID`). Reconnection matches by ID only, never by name — duplicate player names in one room are supported. **The ID is public** (every page in a room sees the players list), so a second UUID per browser proves who a browser is: the secret, `localStorage['whoami-player-secret']` (`PLAYER_SECRET`). Every join sends it (`/api/join-game` refuses one without it); the first join records it in `game.secrets`, later joins as that player — a reload, a second tab, a return to a started round (the `recentlyLeft` snapshot keeps it) — must match ("This player is playing in another browser"), and `join-room` registers a socket only with it (`checkPlayerSecret`). The server keeps only a hash of each secret (one browser uses one secret in every room); the hashes stay in the room's storage: never in a broadcast, an answer or the log (`forLog` in worker/room.js shortens what a request sent and marks a photo). `/api/join-game` answers "Game not found" before it asks for the secret, so a page without one (an old page left open across a deploy) learns that the room is gone. A stored ID that is not a valid UUID is regenerated on load (`PLAYER_ID_PATTERN` in utils.js): the server silently replaces non-UUID IDs, which would otherwise duplicate the player on every page load
- **Timeout protection:** the page pings its room every 25 seconds and the room answers `pong` without waking (an auto-response); a page that has heard nothing for a minute and a half takes its connection for dead and connects a new one (more than a minute: a hidden desktop tab gets its timers once a minute), and a page coming back on screen pings at once and reconnects if no answer comes in 5 seconds (room-socket.js; reconnects wait 1 s, doubling up to 5 s, plus a random part). The room, while sockets are open, looks every minute for sockets not heard for 2 minutes and counts them gone (`sweepSilentSockets`, room-base.js) — a phone asleep with its socket open. Disconnected players are marked `isConnected: false` rather than removed, so they can reconnect. Players disconnected for over an hour (`MAX_DISCONNECTED_MS`; "ghosts" — usually the same person returning under a new playerId) are removed by the room's timer (`removeStaleDisconnectedPlayers` in game-logic.js) and broadcast as a regular `player-left` — **only while a page of a player is open**: a group whose phones all slept through a break finds its room as it left it. When the first page comes back after such a gap, every player still offline gets a fresh hour (`restartGhostClocks`); otherwise the first one back would see the others removed. An hour is the owner's decision: a player whose phone sleeps through a break stays on everyone's list; the price is a ghost in the lobby keeping Start disabled for up to that hour, unless someone gives it a character; in a started game the `recentlyLeft` snapshot still lets the same ID return
- **Keep screen awake:** while a round is on — from Start until every envelope is open, or until Restart — the room page holds a screen wake lock (`keepScreenAwake()` in wake-lock.js, called from `updateGameDisplay()`, so a reload or a return to a started round takes it too): players look at the others' tags for minutes without a touch. No timer: a phone left on the table during the round stays lit, after the last envelope it sleeps as usual. Silent, like the owner's Western Setup: no control, no text, a browser without the API or one that refuses (battery saver) shows nothing. The browser drops the lock whenever the page leaves the screen; coming back (`visibilitychange`) and any tap ask again — the tap also covers a browser that refuses a lock asked for without one (the round starts for most players with the server's message). Permissions-Policy (`public/_headers`) must not forbid `screen-wake-lock`; `tests/e2e/wake-lock.spec.js` checks the real Chromium lock too
- **Connection tracking:** whose a socket is lives in the socket itself — its attachment, which survives the room's sleep: `{ role: 'player', playerId }` after `join-room`, `{ role: 'waiting', playerId }` after `ask-to-join`, no role otherwise. Two tabs of one browser are one player, and on page refresh the new socket often connects *before* the old one closes: a player goes offline only when their last socket goes. "Online" means a live page: `join-room` marks the player connected (`markPlayerConnected`, and only a player of that room gets the role), the last close marks them offline; the HTTP join does neither, so a player whose room page never opens (a closed tab) becomes a ghost instead of staying "online" forever. A room that went down with its sockets (it hears none of them close) puts things right as it loads: a player marked online without a socket goes offline, a request without a waiting socket goes. `isConnected` is the server's bookkeeping only — the page does not show it
- **The shared part:** `worker/room-base.js` and `public/js/room-socket.js` know nothing of the game — no event names, no texts, no rules — so the owner's next app with rooms copies them unchanged (the owner's decision); the game's part is `worker/index.js`, `worker/room.js`, `game-logic.js` and the pages. They have no tests of their own: the game's browser tests cover them. When unsure where code goes, it goes into the game's part

## Rules (important!)
1. **Bump the icon cache version in `CACHE_NAME`** (public/sw.js, e.g. `whoami-game-v1.6.0` → `v1.6.1`) **when you change the icons** (drawn in `scripts/icon.html`, taken by `node scripts/icons.js`). Only icons are cached, so HTML/CSS/JS changes reach players without it. This is not the app version — that one is in package.json (`docs/release.md`)
2. **No code duplication across files** — shared frontend code goes to `public/js/utils.js`
3. **Update tests whenever logic changes**: a game rule → Jest with `game-logic.js`; what the player sees or does → a browser test in `tests/e2e/` (`docs/testing.md`). Run `npm test` before committing
4. **Localize all UI text** — every user-facing string needs both `en` and `ru` entries in `public/js/translations.js`. `tests/translations-real.test.js` fails if a key exists in only one language. An error the server sent is shown through `serverErrorText()` (utils.js). Static markup supports `data-i18n` (text), `data-i18n-placeholder`, `data-i18n-title` and `data-i18n-aria-label` (for icon-only buttons)
5. **Never build DOM from user data with `innerHTML`** — player names and characters go through `textContent` (see `createAlertElement()` in utils.js and `updatePlayersList()` in game-room.js)
6. **Debug output goes through `debugLog()`** (utils.js), never `console.log` in `public/js` (ESLint fails on it). It prints only after `localStorage.setItem('whoami-debug', 'on')` and a reload. `console.warn`/`console.error` are for real problems. The Worker and the rooms keep `console.log`: it is what Workers Logs show (`observability` in wrangler.jsonc; live: `npx wrangler tail whoami-game`)
7. **The pages share names through plain `<script>` files** — a top-level name in utils.js or translations.js is visible to the scripts loaded after it. ESLint checks each file on its own, so a file lists what it takes from the others in `/* global ... */` and what it gives in `/* exported ... */`
8. **Only the game's own code runs on its pages** (Content Security Policy, `public/_headers`) — no `style="..."` or `on...="..."` attributes, neither in the markup nor in HTML a script builds: looks go through classes in style.css, handlers through `addEventListener`; a script may still set `element.style`. `tests/code-structure.test.js` checks the attributes, the browser tests' guard any other blocked code. Third-party code goes to `public/vendor/`, never a CDN. A new source in the CSP (another site, `data:`, `blob:`) is a deliberate decision with a comment in `public/_headers` (and the same value in `worker/security-headers.json`)

## Gotchas
- **Sticker colors are picked by the server** (`stickerColors` in game-logic.js); the browser only renders `player.stickerColor` as the `color-<name>` class, so every color needs a `.character-sticker.color-<name>` rule in style.css (`tests/improved-sticker-colors.test.js` checks). The rule sets `--deep`: the pin and the letters of the character's tag. The avatar pool lives **only** in `public/js/game.js`; the server does not need it
- `game-logic.js` must stay free of Cloudflare imports (CommonJS, Node's `crypto` through `nodejs_compat`) so Jest tests it in Node; its functions take a `Map` of games, and a room passes a Map of its one game
- Validate on the server, not just in the UI: `sanitizePlayerName` / `sanitizeAvatar` / `sanitizeCharacter` enforce the input limits, `assignCharacter` refuses to change characters once `state !== 'waiting'` (a late `blur` event can arrive after Start Game) - except a first, non-empty character for a player who has none (a newcomer let into the round), and `startGame` refuses while a player has no character (someone can join at the moment Start is pressed)
- **Input limits (128 chars for names and characters) exist twice** — `game-logic.js` for the server and `public/js/utils.js` for the browser (a browser script cannot `require()` a Node module). `tests/input-limits.test.js` fails if they drift apart. Lengths are counted by character, not UTF-16 code unit, so an emoji counts as one and is never cut in half
- **The player ID pattern exists twice** — `PLAYER_ID_PATTERN` in `game-logic.js` and `public/js/utils.js`; `tests/input-limits.test.js` keeps them equal
- **Custom avatar (uploaded photo) validation also exists twice** — `isCustomAvatar()` + `MAX_CUSTOM_AVATAR_LENGTH` + `CUSTOM_AVATAR_PATTERN` are mirrored in `game-logic.js` and `public/js/utils.js`; `tests/input-limits.test.js` keeps them in sync. The photo is shrunk in the browser (game.js `processAvatarFile`) to a small square JPEG data URL (`CUSTOM_AVATAR_SIZE`) and stored in the same `player.avatar` field the emoji uses, so the room's storage and every broadcast carry it for free. The anchored pattern only allows `data:image/(png|jpeg|webp);base64,...` — never loosen it (XSS), and only render it via `img.src` behind the `isCustomAvatar()` guard. A join carries one avatar: the Worker refuses a body over 64 KB
- **Server error texts exist twice** — the server answers in English (`error: '...'` in game-logic.js and worker/index.js, `this.send(ws, 'error', '...')` in worker/room.js), and `serverErrors` in translations.js holds their Russian copies, keyed by the English text. `tests/translations-real.test.js` fails if a text the server sends has no copy or a copy outlives its text; it finds the texts written literally, in those forms, so a server error is never built from pieces. Rewording a server error means rewording its key too; game-room.js also compares `'Game not found'` and `'This request has already been answered'` itself
- `game-room.js` rebuilds the whole players list (`updatePlayersList()`) on updates instead of patching individual stickers — per-sticker DOM patching caused sync bugs, don't reintroduce it. Rebuilds are **skipped while a character input is open**, so anything that ends editing (game start, socket error) must call `cancelActiveEdits()` first or the UI freezes
- Dynamic text rendered from JS (game status, player cards) does not react to `data-i18n`. `setLanguage()` fires a `languagechanged` event; game-room.js listens and re-renders. Prefer static markup for controls (like `#shuffleAvatars`) so `data-i18n*` and keyboard focus just work
- The avatar selector sits inside `<form id="playerForm">`, which has a submit button. **Any `<button>` added there needs `type="button"`** or clicking it joins a game
- **Hover effects only for a mouse** — a `:hover` rule in style.css goes inside `@media (hover: hover) and (pointer: fine)`: on a touch screen the hover state sticks after a tap, and a tapped tag would stay straightened (`tests/e2e/styles.spec.js` checks)
- Mobile virtual keyboard: call `input.focus()` synchronously inside the click handler (no `setTimeout`) — otherwise iOS/Android won't open the keyboard
- Character assignment: players cannot assign a character to themselves; submitting empty/whitespace text removes the assignment (the card returns to the "+ Assign character" button). Escape restores the original character
- Sticker colors are assigned once when a player joins and never change; unique for up to 7 players, then cycled. Exception: your own hidden character renders as `.character-sticker.mystery` — a sealed envelope with a wax seal `span.seal` "?" (the wax is the app icon's, drips and all: `img/seal.svg`, a deliberate copy of `scripts/icon.html`'s seal that `tests/wax-seal.test.js` keeps equal; the "?" is the span's text), deliberately NO player color — until revealed; a newcomer let into a started round sees it unsealed (`open-envelope`) until a player gives them a character. A revealed player's card gets the class `revealed` (gold paper, a gold ring round the tag)
- **Characters are tags pinned to the cards**: every other card's tag leans the other way (`:nth-child(even)`; the list is in join order everywhere, so each tag leans the same way for everybody). A tag is a flex box, so a long word needs `overflow-wrap: anywhere` — `break-word` lets it run out of the tag (`room.spec.js` checks a 128-letter word). On a phone (style.css's `max-width: 768px` block) the names and tags are written larger: players read them at arm's length, the phone on the table. "+ Assign character" on someone else's card is a real `<button>` (`btn btn-outline-primary add-character-btn`, text from `assignCharacter`) built by game-room.js
- **Share buttons** (`#shareButton` in the lobby's invitation, `#gameShareButton` in a started game's; both run `shareRoomLink()`): `navigator.share` must be called with no `await` before it in the click handler (iOS rejects otherwise); `AbortError` (user closed the share sheet) is intentionally silent; unsupported browsers fall back to `copyRoomLink()`. Tests use `stubShare()` (`tests/e2e/helpers.js`) — a real click opens the OS share sheet, which blocks automation
- **Copy Link writes to the clipboard** (`copyRoomLink()`: `navigator.clipboard.writeText`): a started game's invitation has no link field to select. A page the clipboard is closed to (plain http, as a phone on the home network) falls back to selecting `#shareLink` and `execCommand('copy')`. Headless Chromium lets a page write and read the clipboard only with `grantPermissions(['clipboard-read', 'clipboard-write'])`: `share.spec.js` reads the copy back that way, and with `clipboard-read` alone it tests the fallback
- **Browser tests run with `reducedMotion: 'reduce'`** (Bootstrap modals open without their fade), and axe scans with CSS transitions switched off: `.mobile-modal-btn` animates its own color change, which reduced motion does not stop, and a color measured half-way fails contrast. The rule goes into the page's own stylesheet with `insertRule`: an added `<style>` tag is inline code the CSP blocks. A check that "nothing happened" reads the page once at a known moment — a flash like "✅ Copied!" disappears by itself (`docs/testing.md`, rule 4)
- **The Content Security Policy allows images as `data:` and `blob:`** besides the game's own files: Bootstrap draws its icons as `data:` images, photo avatars are `data:image` URLs, and an uploaded photo is opened at a `blob:` address before it is shrunk (game.js `loadImageFromFile`). Everything else — scripts, styles, connections (the room's WebSocket included), fonts — only from the game's own site. Buy Me a Coffee is therefore a plain link (`.bmc-button` in the landing page footer), not the service's widget script: a small playbill plate, English in both languages like the sign, its name the words it shows (`lang="en"`); the cup in it is the service's own logo file, unchanged (`img/bmc-cup.svg`) — their terms forbid changing their marks. The browser tests' guard fails on any violation; the one it ignores is the test tool's own: a trace Playwright records (a run with `--trace on`; traces are off by default, `docs/testing.md`) fetches a `blob:` image of the page
- **The sign** ("WHO AM I?", drawn after escapist-web's) is an inline `<svg class="brand-sign">` in three deliberate copies — index.html and game.html (the `h1`), 404.html (a `<p>`: its `h1` is "Page not found"); `tests/brand-sign.test.js` keeps them equal. Unlike escapist-web's drawing, the name is Ultra and has no shadow copy: Abril's hairlines under the dark copy were hard to read. It is a logo: English in both languages, `aria-label="Who am I?"`, and its `h1` carries **no** `data-i18n` (a translation would replace the drawing with text) — the page's language shows in the subtitle and the tab title. Its fonts come from style.css by class: a `<style>` inside the SVG is inline code the CSP blocks. The stars are polygons: no font of the game has ★, the system font would draw it differently on every phone. `scripts/og-image.js` takes the sign from index.html, and escapist-web can take `svg.brand-sign` from production
- **Fonts are the game's own files** (`public/fonts/`, the CSP allows fonts only from the site): Fira Sans Condensed sets all the text (narrow like a playbill, yet easy to read; it replaced Oswald, whose tight letters were hard to read in sentences) — Latin and Cyrillic are separate files by `unicode-range`, and there are no italic files (nothing is italic; the browser would slant the letters itself). The sign: Ultra (no Cyrillic) draws its name, Oswald (Latin 600 only) its two small lines; Abril Fatface draws only the seal's "?" (and the app icon's); both have `font-display: block`, and Ultra a `preload` in the three pages: a logo flashing in a fallback serif looks worse than a short pause. Ultra's license is Apache 2.0, the others' SIL OFL. `styles.spec.js` checks the faces load, Cyrillic included, and the envelope test in `game.spec.js` checks Abril
- **Colors are tokens on `:root`** in style.css (`--paper`, `--ink`, `--red`…). Bootstrap is repainted through its own variables — `--bs-btn-*` for buttons, `--bs-secondary-color` (so `text-muted` and `form-text` are `--ink-soft`), `--bs-modal-*`, `--bs-alert-*` — never `!important`. The main button is ink, secondary buttons an ink outline; **red only for accents and for what cannot be undone** (Reveal, Leave, Restart). The app's color `#7e1a13` (the top of the curtain) is written in the three pages' `theme-color` and in the manifest (`tests/manifest.test.js` keeps them equal)
- **Link preview tags live in two copies** — the `<head>` of index.html and game.html (the room link is the one players share). A messenger's bot runs no scripts, so the card's text is fixed markup, not `data-i18n`, and its addresses are absolute: they hold the production domain (`docs/publishing.md` lists every place). game.html has no `og:url` (one file serves every room) and has `noindex`; rooms are never closed in robots.txt, which would also stop X's card. `tests/e2e/link-preview.spec.js` reads the pages as a bot does and keeps the two cards equal. The picture is taken from `scripts/og-image.html` by `node scripts/og-image.js`; messengers keep a picture by its address, so a new look gets a new file name (`og-image-2.jpg`, written in the script and in both cards)
- Button feedback flashes ("✅ Copied!") set `textContent`, which flattens the inner `data-i18n` span — after the first flash that button's label stops reacting to language switches until reload (long-standing quirk of Copy Link, shared by Share via `copyRoomLink()`)
- **The room socket drops what it cannot send** — `RoomSocket.emit` while not connected sends nothing: a move goes through `sendMove()`, which waits for the room. Tests drop a connection with `socket.ws.close()` and hold a page's `join-room` with `holdRoomJoin()` (it wraps `WebSocket.prototype.send`; `docs/testing.md`)
- **A deploy keeps the sockets open**: a sleeping room wakes on the new code, its sockets and storage in place; a room that stays awake runs the previous code until it sleeps, new pages included. So for a while after a deploy a room may run the old code next to new pages: a change of the socket protocol must still work with a room on the previous version. A room that Cloudflare does restart drops its sockets: the pages reconnect, and the room puts its bookkeeping right as it loads (Connection tracking)
- **A new or renamed room class needs a new migration entry** in wrangler.jsonc (`migrations`: `new_sqlite_classes` for a new class — SQLite storage is the kind the free plan has —, `renamed_classes` for a new name); a migration that deletes a class deletes every room's storage with it
- **`public/` is uploaded as it is**: a file in it is a file of the site, unless `public/.assetsignore` names it (`.DS_Store` from a Mac); `_headers` and `.assetsignore` themselves are not served (`not-found.spec.js` checks)
- **PWA link capturing is a platform matter, not a bug.** iOS cannot open links in an installed web app at all (Apple limitation — links always open the browser/webview; no web-side fix exists). Android (installed via Chrome) captures in-scope links because `scope: "/"` covers `/game/*`; messenger in-app browsers bypass this. `launch_handler: navigate-existing` in manifest.json makes a captured link reuse the open app window (Android/desktop). `tests/manifest.test.js` guards these fields
- **The service worker caches icons and nothing else.** The game requires a live server (a room lives on the server), so offline support is pointless, and caching HTML/JS only ever produced "player stuck on an old version" bugs. The worker exists for installability plus free icon caching. `tests/service-worker.test.js` fails if HTML/CSS/JS is added back to the cache. Icon matching is by **exact pathname** — an earlier substring check matched every URL because `'/'` was in the list. **Any change to sw.js, even a comment, is a new worker**: browsers install it and pwa.js shows every open page the "Update available — Reload" banner, so edit sw.js only for a real reason

## Git Workflow (git flow)
Steps and commands: `docs/release.md`.
- `master` — production. **Every push to `master` deploys**: Cloudflare's Workers Builds installs the packages and runs `npx wrangler deploy`; no other branch is built. Never commit to it directly
- `develop` — integration branch. Never commit to it directly
- **All changes go in feature branches**: `feature/<short-name>` from `develop`, finished with a local `git merge --no-ff` into `develop` (no Pull Requests), then the branch is deleted
- Before every merge: `npm test` must pass
- **Release**: `release/<x.y.z>` from `develop` → bump the version (`npm version minor --no-git-tag-version`) → merge `--no-ff` into `master`, tag `v<x.y.z>`, merge back into `develop` → push `master`, `develop` and tags. **Push to `master` only after the owner confirms** (it deploys production), then check production (`docs/release.md`)
- **Hotfix**: `hotfix/<x.y.z>` from `master` → a test that fails on the old code, the fix, a patch bump → merge `--no-ff` into `master` (tag) and `develop`
- A room lives in its own storage and keeps its sockets across a deploy (Gotchas): a game in progress goes on

## Decisions (why it is so)
The owner's decisions, with the reason.
- **No CI**: `npm test` on the developer's machine is the only check before code reaches `develop` and production
- **The repository is public — a showcase**: anyone may read the code and learn from it; issues are welcome, pull requests are not expected (only collaborators can open them). The code is MIT (`LICENSE`); the sign, the app icon and the link preview picture are not covered (README, License). Vulnerabilities are reported privately (`SECURITY.md`). New commits use the owner's GitHub noreply address as author and committer (`includeIf` in `~/.gitconfig`); older history keeps the personal address
- **The version is written only in package.json**: the server reads it (`/api/version`), the pages ask the server — no copy to keep in sync
- **Online only, no offline mode**: a room lives on the server (see the service worker gotcha above)
- **Cloudflare Workers + bare Durable Objects**: the owner plans more apps with rooms, each at no extra cost. Cloudflare's free plan is per account, not per app, and over a limit the requests fail until midnight UTC — there is no bill; Workers Paid would cover every app at once. One Durable Object per room: a room's state, sockets (the WebSocket Hibernation API: a sleeping room costs nothing) and timer in one place. Bare Durable Objects, no PartyServer or partysocket: fewer dependencies, all the code in sight, and the shared room layer becomes the pattern for the next apps. What counts against the free plan: requests a day for all the owner's apps together (a socket's connection is one, the messages it sends count twenty to one; static files nothing), the rooms' time awake and the rows they write — check the current numbers on Cloudflare's pricing page before relying on them
- **Locally `wrangler dev`**, the Cloudflare runtime on the Mac: the Worker, its rooms and the files together, as in production
- **Browser tests in Chromium only** — a phone (Pixel 7) and a desktop, like the owner's other apps; WebKit (Safari) is not covered
- **Behaviour is tested through the pages, never by searching the code**: a test that looks for `navigator.share` in a file stays green while the button is broken. Tests act like players — through pages, buttons and the server's answers, never through server memory — so the same suite runs against production, and no test keeps its own copy of the game's code. A rule about how the code is written may be checked by reading the files (`tests/code-structure.test.js`), like the checks of the deliberate copies listed in the gotchas
- **The look follows the sign**: a parlour-game playbill — cream paper with a rule inside its edge, dark brown ink, the sign's red — on a theatre curtain; characters are tags pinned to the player cards, your own a sealed envelope; the app icon is the envelope's wax seal
- **The link preview card is in English**, like the owner's other apps: a bot cannot pick the reader's language
- **Bootstrap is local, not on a CDN**: the Content Security Policy allows only the game's own site, and the owner's apps share one Bootstrap (`public/vendor/bootstrap/`)
- **Docs hold principles, not history**: CLAUDE.md, `docs/` and the skills say how things work and why; no development history, dates or measured numbers (sizes, counts, timings) — those live in the code and in git. A design spec or plan of a feature leaves the repository once the feature is merged; what stays true goes here
