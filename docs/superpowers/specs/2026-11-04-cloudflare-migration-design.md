# Перенос whoami на Cloudflare Workers + Durable Objects — проект

Статус: ждёт одобрения владельца. По правилу проекта («docs hold principles, not history») документ уходит из репозитория после слияния; то, что останется верным, переезжает в CLAUDE.md и `docs/`.

Пометки: **(владелец)** — решил владелец; **(моё решение)** — решение автора проекта, владелец может его поменять; без пометки — следует из кода, CLAUDE.md или разговора.

## Зачем

- **Render Free мешает игре.** Сервис засыпает после 15 минут без запросов и просыпается около минуты. Комнаты живут в памяти процесса, и деплой или перезапуск их теряет: диска на бесплатном плане нет, поэтому комнату возвращает только копия в браузере. Своих доменов на аккаунт Render два, и оба заняты (flying, western).
- **Дальше будут другие приложения с комнатами (владелец),** и каждое новое не должно стоить денег. Лимиты бесплатного плана Cloudflare Workers общие на аккаунт, а не на приложение. Если их перерасти, Workers Paid стоит $5 в месяц за все приложения вместе.
- **whoami — пилот.** Тонкий слой комнаты на голых Durable Objects станет образцом для следующих приложений.

## Цели

1. whoami работает на Cloudflare Workers + Durable Objects, по одному Durable Object на комнату.
2. Для игроков ничего не меняется **(владелец: «в игре пока ничего не меняем»)**: те же страницы, правила, вид, тексты и поведение, описанное в CLAUDE.md («How it works», «Gotchas»). Единственное заметное отличие — срок жизни брошенной комнаты (ниже).
3. Комната переживает деплой и перезапуск у Cloudflare: её состояние лежит в хранилище, страницы переподключаются, партия продолжается.
4. Переезд плавный **(владелец)**: Render работает, пока новая версия не готова, и удаляется последним.

## Не цели

- Новые функции и изменения игры. Пока ветка переноса открыта, в whoami ничего не добавляется.
- Выбор домена — отдельный разговор с владельцем до этапа 2 **(владелец)**.
- Ограничение частоты создания комнат (идея из CLAUDE.md) — не в этой работе.
- Перенос комнат с Render: комната живёт часы, её не переносим.
- Перенос других приложений владельца.

## Анти-цели (провал, даже если всё работает)

- Игроки заметили переезд чем-то, кроме нового адреса: сломалось поведение, пропал перевод, пропали заголовки безопасности.
- Ослаблены защиты и проверки: CSP, правила кода из CLAUDE.md, проверка секрета игрока, набор тестов.
- Логика игры перетекла в слой Cloudflare. `game-logic.js` остаётся чистой логикой, которую тестирует Jest.
- Переезд требует денег. Всё укладывается в бесплатный план; выбор, который требует Workers Paid, — решение владельца.
- Render сломан или перестал работать до того, как новая версия готова.

## Условия переключения (владелец)

Игроков переводят на новую версию, когда:

1. она развёрнута на Cloudflare без ошибок;
2. весь набор тестов против неё проходит (`BASE_URL`, как `npm run test:e2e:prod`);
3. у неё задан постоянный домен.

Живые игры перед переключением — не условие.

## Решения владельца по технике

- **Голые Durable Objects** — без PartyServer и partysocket. Причины: меньше зависимостей, весь код на виду, а слой комнаты, написанный для whoami, станет образцом.
- **Общая часть — в отдельных файлах внутри whoami.** Основа комнаты на сервере и обёртка сокета на странице ничего не знают про whoami. Следующее приложение копирует их без изменений, как владелец уже переносит между приложениями Bootstrap и wake-lock. Отдельного npm-пакета нет.
- **Локально — `wrangler dev`** (движок Cloudflare на Mac, Durable Objects и статика вместе). `npm start` запускает его.
- **Тесты.** Jest остаётся для того, что не зависит от сервера. Тесты HTTP API (сейчас Jest + supertest на `app`) переезжают в Playwright (`request`) и, как браузерные, идут и против продакшена. Vitest с пулом Workers не берём.
- **Выкатка.** На этапе 1 — вручную, `wrangler deploy` из ветки переноса на временный адрес `*.workers.dev`. После переключения — Workers Builds: каждый пуш в `master` выкатывается сам, как сейчас на Render. Правило «пуш в master — только после подтверждения владельца» остаётся. GitHub Actions не используем.
- **Комната без открытых страниц удаляется через 2 часа** после того, как закрылась последняя страница.
- **Уходят:** восстановление из копии в браузере (`/api/recreate-game`), резервные копии на диске (`game-backups.js`, `GAMES_DIR`), цикл keep-alive.

## Устройство

### Части

Код делится на две части **(владелец)**:

- **Общая часть** — файлы, которые следующее приложение с комнатами копирует без единой правки. На сервере это основа комнаты: приём сокетов и их учёт с переживанием спячки, рассылка (всем, всем кроме одного, конкретным сокетам), разбор сообщений `{ event, data }` с защитой от испорченных, сохранение состояния в хранилище, таймер, автоответ на пинги. На странице это обёртка сокета. Ни имён событий whoami, ни правил игры, ни текстов whoami в этих файлах нет. Ошибка «Something went wrong, please try again» — текст whoami, поэтому общая часть получает его извне или зовёт обработчик whoami.
- **Часть whoami** — обработчики событий игры поверх основы, маршруты HTTP, `game-logic.js`, страницы.

Граница проходит там, где следующему приложению пришлось бы что-то править. Если сомневаешься, кладёшь в whoami: общую часть проще расширить потом, чем вычищать из неё чужие правила.

- **Worker** — точка входа. Отдаёт статику из `public/` (Workers static assets), отвечает на `/game/:code` и `/api/*`, принимает WebSocket и передаёт его Durable Object комнаты, ставит заголовки безопасности на свои ответы.
- **Комната** — класс Durable Object на SQLite (на бесплатном плане доступен только этот вид), по одному объекту на код комнаты (`idFromName(code)`). Держит игру, сокеты своих страниц (WebSocket Hibernation API) и таймер (alarm).
- **`game-logic.js`** остаётся без импорта Cloudflare, как сейчас он без Express и Socket.IO, и Jest тестирует его как сейчас. Он использует `crypto` из Node (`createHash`, `randomInt`, `randomUUID`): в Workers это работает с флагом `nodejs_compat`. Его функции принимают `games` (Map всех комнат). Внутри Durable Object комната одна, и как с этим быть — Map из одной комнаты или новые сигнатуры — решает строитель.
- **Страница.** Вместо клиента Socket.IO — свой небольшой файл поверх браузерного `WebSocket` в `public/js/`, обычный `<script>` без сборки, по правилам 2 и 7 из CLAUDE.md. Интерфейс как у Socket.IO (`on`, `emit`, события `connect` и `disconnect`), чтобы `game-room.js` менялся как можно меньше. Обёртка переподключается сама и замечает мёртвое соединение (телефон проснулся), как сейчас Socket.IO (ping каждые 30 с, тайм-аут 2 минуты). Строка `/socket.io/socket.io.js` уходит из `game.html`.

### Протокол сокета

- Сообщения — JSON вида `{ event, data }`. События те же, что сейчас: `join-room`, `ask-to-join`, `admit-player`, `decline-player`, `assign-character`, `start-game`, `reveal-character`, `restart-game`, `leave-game`; от сервера — `game-state`, `player-joined`, `player-reconnected`, `player-disconnected`, `player-left`, `character-finalized`, `game-started`, `character-revealed`, `player-revealed-notification`, `game-restarted`, `join-requested`, `join-request-closed`, `join-request-ended`, `error`.
- Сохраняется всё поведение из CLAUDE.md, в том числе:
  - рассылка комнате включает отправителя (как `io.to(room)`), а `player-disconnected` получают все, кроме отключившегося;
  - ход делает игрок, за которого зарегистрирован сокет (`join-room` после проверки секрета), никогда не ID из сообщения; незарегистрированный сокет получает «You are not in this game» и ничего не слышит о комнате;
  - новичок, ждущий допуска, не слышит комнату, и его сокет никогда не считается сокетом игрока;
  - сокет, вошедший (`join-room`) после того как его игрок ушёл или комнаты нет, получает `player-left` для себя;
  - выход в одной вкладке выводит из комнаты все вкладки игрока;
  - порядок входа страницы прежний: сначала HTTP join, потом `join-room`; ходы ждут в `sendMove`, пока сокет не вошёл (`game-state`);
  - испорченное сообщение не роняет комнату (сейчас это `safeHandler`): ответ `error` «Something went wrong, please try again».

### Комната и спячка

Это главное отличие от нынешнего сервера, и строителю важно его учесть. Cloudflare усыпляет комнату между сообщениями и может выгрузить её из памяти в любой момент. Это не редкий перезапуск, как на Render, а обычное дело. Поэтому всё, что сейчас живёт в памяти процесса, должно восстанавливаться без потерь:

- **состояние игры** — из хранилища комнаты, которое сохраняется после каждого изменения. `serializeGame()` и `restoreGame()` в нынешнем виде для этого **не годятся**: они написаны для чужих данных (копии на диске и в браузере) и после перезапуска. `restoreGame()` сбрасывает всем `disconnectedAt` на «сейчас», и при пробуждении на каждый alarm «призраки» не уходили бы никогда. Кроме того, он теряет `recentlyLeft`, и ушедший уже не вернулся бы в начатую партию со своим персонажем. Комната должна сохранять и поднимать всё состояние как есть: `recentlyLeft`, секреты, `disconnectedAt`, время последнего изменения. Проверки `restoreGame()` нужны только для чужих данных, а свои данные комнаты такими не являются;
- **какой сокет чей** (сейчас `createConnectionTracker()`) — из самих сокетов: `getWebSockets()`, теги, `serializeAttachment`. Поведение как сейчас: две вкладки — один игрок; при обновлении страницы новый сокет часто приходит раньше, чем закрывается старый; игрок уходит в офлайн, только когда закрылся его последний сокет;
- **заявки новичков** (`joinRequests`). Сейчас они не сохраняются, потому что перезапуск сервера редок; здесь они должны переживать спячку. Правило прежнее: заявка живёт, пока живы страницы ожидания новичка, и уходит вместе с последней. Как её восстанавливать — решает строитель;
- **пинги** — через автоответ (`setWebSocketAutoResponse`), чтобы они не будили комнату.

Хэши секретов лежат в хранилище комнаты и больше нигде: ни в рассылке, ни в ответе, ни в логе. Сейчас так же с резервными копиями на диске.

### Жизнь комнаты

- Пока открыта хоть одна страница игрока этой комнаты, комната живёт.
- Когда закрылась последняя страница игрока, комната ставит таймер на 2 часа **(владелец)**. Кто-то вернулся — отсчёт сбрасывается. Таймер сработал — комната стирает своё хранилище (`deleteAll`), и код снова свободен. Ждущие новички в этот момент получают `join-request-ended` с `retry`, как сейчас, когда уходит последний игрок.
- Последний игрок нажал «Выйти» — комната удаляется сразу, как сейчас.
- **«Призраки»** (игроки, отключённые дольше часа, `MAX_DISCONNECTED_MS`, решение владельца в CLAUDE.md) уходят по таймеру комнаты и рассылаются как обычный `player-left`, но **только пока в комнате открыта хоть одна страница игрока (моё решение)**. Когда страниц нет совсем, никого не удаляем, и компания, вернувшаяся в течение 2 часов, застаёт комнату такой, какой оставила. Сейчас тот же итог даёт копия на диске.
  - **Часы «призраков» после перерыва (моё решение).** Когда после перерыва без страниц возвращается первая страница игрока, час каждого игрока, который всё ещё офлайн, начинается заново с этого момента. Так сейчас делает `restoreGame()`, и именно это даёт нынешний итог. Иначе первый вернувшийся после перерыва дольше часа удалил бы всех остальных: они получили бы «вышел из игры», а в лобби потеряли бы персонажа и место в списке. Цена: настоящий «призрак», оставшийся с прошлого раза, держит Start в лобби ещё до часа.
- **Что игроки могут заметить:** комнату, брошенную больше чем на 2 часа, по старой ссылке уже не поднять. Сейчас её иногда поднимала копия в браузере.
- **Что становится лучше:** уходит ограничение из CLAUDE.md («Limit» в «Player identity»): у комнаты, поднятой из браузерной копии, нет секретов, и кто-то, зная ID с карточек, мог занять чужое место.

### HTTP

- `GET /game/:code` — сначала проверка формата кода. Неверный код не доходит до Durable Object: иначе случайные адреса создавали бы объекты. Потом комнату спрашивают, есть ли игра: есть — отдаётся `game.html`, нет — редирект на `/?error=room-not-found`.
- `POST /api/create-game` — Worker придумывает код, комната создаёт игру, если она пуста. Занят — берётся другой код.
- `POST /api/join-game` — передаётся комнате. Рассылка `player-joined` / `player-reconnected` идёт из комнаты по её сокетам. Ответы и порядок проверок прежние («Game not found» до проверки секрета, `waitingForApproval` со статусом 200).
- `GET /api/version` — версия из `package.json` (Worker импортирует файл; правило «версия только в package.json» остаётся).
- `POST /api/recreate-game` удаляется. На странице вместе с ним уходят `saveGameStateToStorage`, `loadGameStateFromStorage`, `clearGameStateFromStorage`, `recreateRoomFromStorage` и ветка «Game not found → восстановить» в `game-room.js`. «Game not found» остаётся: страница уходит на главную с ошибкой, как когда копии нет.
- Предел тела запроса был 1 МБ ради recreate-game. Теперь самый большой запрос — join-game с одной фото-аватаркой (до 32 КБ); новый предел выбирает строитель.
- Любой другой адрес — `public/404.html` со статусом 404.

### Заголовки безопасности

- `SECURITY_HEADERS` (тот же список и та же CSP) стоят на каждом ответе: страницы, файлы, API, 404, редиректы. `connect-src 'self'` покрывает WebSocket того же адреса. Проверяют `site-headers.spec.js` и защитная проверка CSP в браузерных тестах.
- Статика из Workers static assets по умолчанию отдаётся без запуска Worker и тогда, насколько известно, не тратит лимит запросов. Поэтому заголовки для статики лучше задать файлом `_headers`, а Worker ставит их на свои ответы. Если `_headers` для Workers assets не годится, остаётся запуск Worker на каждый запрос (`run_worker_first`), но тогда каждый файл тратит дневной лимит. Это нужно взвесить, а не выбрать молча.

### Логи

`console.log` Worker и комнаты попадает в Workers Logs (включить `observability` в конфигурации) и читается в панели Cloudflare, как сейчас лог Render. Правило прежнее: секрет и аватарки в лог не пишутся (`forLog`).

### Конфигурация и зависимости

- **`wrangler.jsonc`** в репозитории: имя Worker, `main`, `compatibility_date`, `compatibility_flags: ["nodejs_compat"]`, `assets` (каталог `public/`), привязка Durable Object, `migrations` с `new_sqlite_classes`, `observability`. У голых Durable Objects миграции пишутся руками: новый или переименованный класс — новая запись.
- **Зависимости:** `wrangler` — devDependency. `express`, `socket.io` и `supertest` уходят.
- **Удаляются** `server.js` и `game-backups.js`. Их смысл переезжает в Worker и комнату, поведение — без изменений.
- **`render.yaml`** уходит в релизе переключения (этап 2), не раньше.
- **ESLint:** блок для кода Worker и комнаты (среда Workers).
- **Скрипты `package.json`:** `start` и `dev` запускают `wrangler dev`. `test:e2e:prod` и `homepage` меняются при переключении. Скрипт `deploy` — на усмотрение строителя.
- **`public/sw.js` не трогаем:** любая правка показывает игрокам баннер обновления.

### Тесты

- **Jest остаётся** для `game-logic.js`, проверок копий и правил кода. Новые правила игры попадают туда же: например, «призраков» не удалять, когда страниц нет, если это правило живёт в `game-logic.js`.
- **Уходят или переписываются** тесты удаляемого кода: `game-backup.test.js`, `room-recreation.test.js`, `api.test.js` (в Playwright), `connection-tracker.test.js`, `game-cleanup.test.js`, `timeout-protection.test.js` — по судьбе своего кода. В браузерных тестах: `language.spec.js` вызывает `recreateRoomFromStorage`, `leave-and-return.spec.js` подкладывает резервную копию в `E2E_GAMES_DIR`.
- **`tests/translations-real.test.js`** ищет тексты ошибок сервера буквально в `game-logic.js` и `server.js`. Список файлов меняется на новые файлы сервера, а тексты ошибок по-прежнему пишутся буквально (`error: '...'`, `emit('error', '...')` или новый вид вызова, который тест тоже находит).
- **Playwright:** `webServer` запускает `wrangler dev` на порту 3100 с хранилищем во временной папке (`--persist-to`) и никогда не переиспользует запущенный сервер. Против продакшена — `BASE_URL`, как сейчас. Тесты, которым нужно вмешаться в сервер (подложить состояние, ускорить таймеры), только локальные (`test.skip(!!process.env.BASE_URL)`), как сейчас.
- **Общая часть отдельных тестов не получает (владелец):** её проверяют браузерные тесты whoami.
- **Через страницы проверить новое:** партия продолжается после обрыва и переподключения сокета. Что комната переживает деплой, можно проверить и вручную на развёрнутой версии.
- **`docs/testing.md`** обновляется.

## Этапы переезда

### Этап 1 — новая версия рядом с Render

- Ветка `feature/cloudflare` от `develop`. Она живёт долго; исправления из `master` и `develop` вливаются в неё.
- Render всё это время выкатывает `master`, как раньше.
- Выкатка вручную: `wrangler deploy` на `<имя-worker>.<поддомен-аккаунта>.workers.dev`. Перед первой выкаткой владелец один раз входит в аккаунт: `wrangler login`, это интерактивная команда.
- Адрес сайта в карточках превью и остальных местах из `docs/publishing.md` на этом этапе не меняется: домен ещё не выбран.
- Итог этапа: тесты проходят локально и против адреса `workers.dev`.

### Домен — отдельный разговор (владелец)

До этапа 2. Без выбранного домена переключения нет.

### Этап 2 — переключение

Готовится отдельно, когда этап 1 закончен и домен выбран. Требования и порядок:

1. Домен подключён к Worker, условия переключения выполнены.
2. Render перестаёт забирать `master` и остаётся на старой версии. Как именно — выключить автодеплой или перевести на замороженную ветку — решается при подготовке этапа, после проверки, как сервис подключён к Render: если через Blueprint из `render.yaml`, новый `master` может переписать его настройки.
3. Релиз по `docs/release.md`: в `master` приходит новая версия. Workers Builds подключён к репозиторию, рабочая ветка — `master`; выкатку других веток выключить, чтобы выкатывался только `master` **(моё решение)**.
4. Новый адрес вписан во все места из `docs/publishing.md`, в README, CLAUDE.md и `package.json` (`homepage`, `test:e2e:prod`).
5. Старый адрес отвечает редиректом 301 на новый с тем же путём. Способ (маленький сервер на Render или статический сайт Render с правилом редиректа) выбирается на этапе.
6. Переключаться, когда никто не играет: комнаты Render на Cloudflare не переедут.

**Что игроки теряют при смене адреса** — браузер хранит данные отдельно для каждого адреса:
- имя и аватар нужно ввести заново;
- ID игрока и секрет создаются заново сами;
- установленное приложение нужно переустановить с нового адреса.

У Flying Solo старый адрес оставлен без редиректа, потому что там по адресу хранятся сохранённые партии. В whoami ценного по старому адресу нет, поэтому редирект безопасен.

### Этап 3 — удаление Render

Через несколько недель после переключения владелец удаляет сервис в панели Render.

## Лимиты бесплатного плана (проверено 2026-11-04)

- **Запросы:** 100 000 в сутки на весь аккаунт, общие для всех приложений. Подключение WebSocket — один запрос; входящие сообщения считаются по 20 за один запрос, исходящие бесплатны.
- **Durable Objects:** 13 000 ГБ·с работы в сутки, 100 000 записанных строк в сутки, 5 ГБ хранилища.
- **Процессор:** 10 мс на запрос.
- **При превышении** запросы получают ошибку до 00:00 UTC, счёта нет.

Прикидка: вечер whoami на 8 человек — порядка 50 запросов.

## Проверить в самом начале

Короткий прототип на выброс — до основной работы:

- комната на голых Durable Objects с Hibernation API: две вкладки одного игрока, обновление страницы (новое соединение приходит раньше, чем закрывается старое), сон телефона, деплой посреди партии;
- `_headers` для Workers static assets и то, что запросы к статике не тратят лимит;
- `nodejs_compat`: `createHash`, `randomInt`, `randomUUID` из `crypto`;
- Workers Builds: рабочая ветка, выключение выкатки других веток, миграции Durable Objects;
- как сервис подключён к Render (Blueprint или вручную) — к этапу 2.
